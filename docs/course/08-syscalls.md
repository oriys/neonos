# 第 08 课：请求内核帮忙，再回到用户程序

状态：待开始。前置：[第 07 课](07-user-mode.md) 验收完成。分 A、B 两次，每次 45～60 分钟。

## 目标与阅读

实现单字符系统调用，让用户连续请求两次输出，并且确实执行到调用之后。阅读 OSTEP 第 5～6 章的接口与受限执行概念。调用编号和错误码统一采用 [阶段协议](stage-02.md)，它是 neonos 教学约定。

## A 次：收到请求并作出决定

时间：协议 10 分钟、分发 25 分钟、检查复盘 15 分钟。

1. 创建计划中的 `src/syscall.rs`，定义命名常量，按保存现场中的 `a7` 取调用号，`a0` 取参数。
2. 只把 U 模式来源、原因编号 8 的同步异常交给系统调用分发器；内核自己的 `ecall` 不能误当作用户调用。
3. 实现 `putchar`：先检查值是否为 0～127，再发送一个字节，返回 0。先检查再转换，不能把 256 截成 0 当作合法参数。
4. 未知调用返回 -1，非法参数返回 -2。本课尚未实现 `exit`，不要假装退出成功。
5. 将结果写入保存现场里的 `a0`，在内核诊断输出中检查参数、返回值。本次暂保留处理后等待。

## B 次：真正返回

时间：现场恢复 20 分钟、联调 20 分钟、回归复盘 20 分钟。

1. 扩展异常处理的结果，区分“恢复用户”与“报告内核故障并停止”。下一课再增加“结束当前进程”。
2. 已处理的用户 `ecall` 将保存的 `sepc` 前进 4 字节，再返回。这个规则只用于确定的 32 位 `ecall`，不能推广到任意异常指令。
3. 恢复流程按第 07 课约定重新准备用户入口、`sscratch` 和可信返回状态，恢复整数寄存器；用户 `sp` 最后恢复，期间不再从用户栈读取内核现场。
4. 现场中的 `a0` 使用分发器给出的新返回值，其余协议承诺保留的寄存器还原。`scause`、`stval` 是诊断信息，不需要像通用寄存器那样逐项写回。
5. 把用户程序改成先请求 O，再请求 K，逐次检查返回值；成功后进入明确的完成位置，调试观察或通过额外成功标记确认。

用户异常返回机制参考 [RISC-V Supervisor 规范](https://riscv.github.io/riscv-unified-db/manual/html/isa/isa_20240411/chapters/supervisor.html)。正式编码前逐项对齐汇编偏移与 Rust `TrapFrame`，不要仅凭“能输出一次”认定恢复正确。

## 验收实验

| 输入 | 预期 |
| --- | --- |
| `putchar('O')` 后 `putchar('K')` | 输出 OK，两次返回值为 0 |
| 调用号 999 | 返回 -1，随后正常字符调用仍成功 |
| `putchar(256)` | 返回 -2，不输出截断后的字节 |
| 在非返回寄存器放入标记后调用 | 调用后标记不变，用户栈指针不漂移 |

错误结果由用户分支判断；如果结果不对，输出独特的失败标记再停留，避免只看内核打印就漏掉返回错误。

## 常见问题与复盘

| 现象 | 先检查 |
| --- | --- |
| 不断输出 O | 返回地址是否仍指向同一条 `ecall` |
| 只有 O，没有 K | 返回用户时的栈、入口与寄存器是否损坏 |
| 用户收到的返回值是原参数 | 是否只改变了 Rust 局部变量而没写入保存现场 |
| 第二次请求进入错误栈 | 返回前是否重新建立 `sscratch` 约定 |

- [ ] 正常和错误请求均返回，用户分支验证结果。
- [ ] 非返回寄存器与用户栈在两次调用间保持正确。
- [ ] 能区分 `call` 调用普通函数和 `ecall` 请求内核。
- [ ] 原启动路径正常，记录本课额外输出到 [进度记录](progress.md)。

小练习：用连续字符调用输出一行短文字，先不增加字符串指针接口。
