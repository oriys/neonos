# 第 08 课：请求内核帮忙，再回到用户程序

状态：待开始。前置：[第 07 课](07-user-mode.md) 验收完成。分 A、B 两次，每次 45～60 分钟。

## 这课解决什么问题

第 07 课已经完成：

```text
U-mode
  ↓ ecall
S-mode trap
  ↓
内核能识别来源
  ↓
停住
```

现在要把最后一步改成：

```text
U-mode 请求
  ↓
内核检查并执行服务
  ↓ 写返回值
恢复用户现场
  ↓ sret
用户从 ecall 后继续
```

本课先只实现一个简单系统调用 `putchar`，没有字符串指针、没有内存复制、没有 `exit`。

## 先写清“教学系统调用 ABI”

这是 neonos 自己的课程协议，不是 Linux syscall 号，也不是 SBI：

```text
a7 = syscall number
 a0 = 第一个参数，同时承载返回值
```

本课：

| 请求 | `a7` | `a0` 输入 | 成功返回 |
| --- | ---: | --- | --- |
| `putchar` | 1 | 0～127 的 ASCII 字节值 | `a0=0` |
| 未知请求 | 其他 | 忽略 | `a0=-1` |
| 参数非法 | 1 | 不在 0～127 | `a0=-2` |

返回值按 RV64 有符号整数解释。

为了让第一版容易验证，本课约定：

> 内核返回用户时，除 `a0` 作为 syscall 返回值外，其余保存的用户整数寄存器保持 trap 前的值；`sepc` 按系统调用规则前移。

以后如果用户 API 变成遵循普通函数 ABI 的高级语言包装，调用者本身仍要遵守普通 caller/callee-saved 规则；不要把“内核能恢复寄存器”误解成“普通函数 ABI 也保证所有寄存器不变”。

## A 次：内核先能识别请求并给出结果，但仍不返回

### 第一步：只有真正的 U-mode ecall 才进 syscall 分发

进入 syscall 逻辑前至少确认：

```text
来源 SPP = 0
scause 表示同步异常，不是 interrupt
exception code = 8 (environment call from U-mode)
```

存在“当前 Process”不能代替来源判断。S-mode 自己执行的 `ecall` 原因不同，不能误当用户请求。

### 第二步：创建 `src/syscall.rs`

把数字写成命名常量，而不是在 trap handler 里散落：

```text
SYS_PUTCHAR = 1
ERR_UNKNOWN = -1
ERR_INVALID = -2
```

分发器的输入来自**已保存的 TrapFrame**，不是直接相信当前硬件寄存器仍保持用户值。

### 第三步：参数一定先验证再转换

对于 `putchar`：

```text
读取 a0
  ↓
检查 0 <= value <= 127
  ↓ 合法
转成输出字节并发送
  ↓
a0 = 0
```

不能先做窄类型转换：

```text
256 as u8 = 0
```

然后再误判成合法 NUL 字节。

### 第四步：先只观察分发结果

A 次仍然在处理后停住，打印：

```text
syscall=1 arg=79 result=0
```

再测试：

```text
putchar('O') → 0
putchar(256) → -2，不输出截断字节
syscall 999 → -1
```

用户还没有真正收到这些返回值，所以日志要写“kernel decided result=...”，不要提前说“用户已经收到”。

### A 次验收

- [ ] 只有 U-mode ecall 进入分发器。
- [ ] 合法字符成功，非法参数不会先截断。
- [ ] 未知 syscall 与非法参数使用不同返回码。
- [ ] 结果写进保存的 `TrapFrame.a0`，不是只改一个 Rust 局部变量。

## B 次：恢复用户，从 `ecall` 后继续

### 第一步：为什么 `sepc` 必须前移

U-mode 执行：

```text
PC → ecall
```

trap 时 `sepc` 指向这条 `ecall`。

如果返回前完全不改：

```text
sret
 ↓
又执行同一条 ecall
 ↓
再次 trap
 ↓
无限重复
```

RISC-V 的 `ecall` 是确定的 32 位 SYSTEM 指令，所以本课对**已经识别且处理的 U-mode ecall**明确：

```text
sepc = sepc + 4
```

这个规则绝不能推广成“所有异常都 +4”。非法指令可能涉及其他长度或根本不应该继续执行。

实现时还应先确认 `sepc` 位于当前已知用户代码范围，并用不会静默回绕的加法处理边界。

### 第二步：Rust 处理函数返回一个明确动作

不要让 trap handler 到处直接跳汇编标签。可以让 Rust 返回类似概念结果：

```text
TrapAction::ResumeUser
TrapAction::KernelFault
```

下一课再加入：

```text
TrapAction::ExitProcess
```

Rust 先正常返回汇编入口，再由汇编统一执行恢复/停止动作。

### 第三步：返回前重新建立用户 trap 约定

Rust 处理期间 `stvec` 已切回内核故障入口。

真正返回用户前，汇编必须重新准备：

```text
stvec    = 用户来源 trap 入口
sscratch = 可信 trap_stack_top
sepc     = ecall 后下一条用户指令
sstatus  = 经过内核校验的用户返回状态，SPP=0
```

不要把用户可影响的普通内存当成特权状态来源。

本阶段仍没有 S 模式中断源，`sie` 保持课程定义的关闭状态。

### 第四步：按正确顺序恢复寄存器

TrapFrame 中：

```text
a0 = syscall 返回值
其他用户整数寄存器 = 按本课协议恢复原值
```

恢复时，用户 `sp` 要最后处理。

原因：一旦把硬件 `sp` 换回用户栈，汇编就不能再继续从当前可信 trap frame 读取剩余内核数据。

可以先加载所有还需要的信息、释放 trap frame，再最后恢复 user `sp`，执行 `sret`。

### 第五步：用户必须自己验证返回值

把用户程序改成：

```text
putchar('O')
检查 a0 == 0
putchar('K')
检查 a0 == 0
进入成功标记
```

错误路径使用独特的失败标记，不要只依赖内核日志说“result=0”。

真正能证明返回正确的是：**用户执行了 `ecall` 后面的检查和第二次调用。**

## 寄存器哨兵实验

在调用前给几个按本课协议应保持的寄存器和用户栈位置写不同哨兵值。

两次 syscall 后检查：

```text
寄存器哨兵没变
用户 sp 没漂移
用户栈数据没被 trap 栈覆盖
```

如果只是成功输出 `OK`，仍不足以证明完整现场恢复正确。

## 验收矩阵

| 场景 | 用户实际观察 |
| --- | --- |
| `putchar('O')` | 输出 O，返回 0，继续执行 |
| `putchar('K')` | 输出 K，返回 0，继续执行 |
| syscall 999 | 返回 -1，之后仍可正常调用 |
| `putchar(256)` | 返回 -2，不输出被截断字节 |
| 寄存器/栈哨兵 | 两次 syscall 后仍符合协议 |

## 常见问题

| 现象 | 先检查 |
| --- | --- |
| O 不断重复 | `sepc` 是否仍指向同一条 `ecall` |
| 只有 O 没有 K | 返回用户时的 `sp`、`sscratch`、`stvec` 或寄存器是否损坏 |
| 用户读到原参数而不是返回值 | 是否真的写回 `TrapFrame.a0` |
| 第二次 trap 用错栈 | 返回前是否重新设置 `sscratch` |
| 用户返回成 S-mode | 返回 `sstatus.SPP` 是否被内核强制为 0 |
| 内核处理故障被再次分类成 syscall | Rust 处理期间 `stvec` 是否保持内核故障入口 |
