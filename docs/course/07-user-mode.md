# 第 07 课：第一次进入用户态

状态：待开始。前置：[第 06 课](06-process.md) 和第一阶段真实实现完成。建议拆成 A、B、C 三次，每次 45～60 分钟。

## 本课只完成一件大事

让一个受控的内嵌程序：

```text
从 S-mode 内核
  ↓ sret
进入 U-mode
  ↓ 执行 ecall
重新陷入 S-mode
  ↓
内核确认：它真的来自 U-mode
```

此时**不返回用户程序**。第 08 课才实现系统调用返回。

阅读 OSTEP 第 6 章 Direct Execution，只关注一个问题：

> 如果允许用户代码直接在 CPU 上执行，内核怎样保证自己还能重新取得控制权？

架构细节按 [RISC-V Supervisor 规范](https://docs.riscv.org/reference/isa/priv/supervisor.html) 查询 `sstatus`、`sscratch`、`sepc`、`stvec` 和 `sret`。

## A 次：先准备用户代码和三类栈，不切换模式

### 为什么不能直接跳到一段“用户代码”

第 06 课只有 Process 数据模型。真正运行至少还需要：

```text
用户代码
用户寄存器初值
用户 sp
trap 时可信的内核栈
```

这些资源今天才第一次出现，所以现在才加入 Process/运行记录。

### 第一步：写一个最小用户程序

在计划中的 `src/user.S` 放一段只使用整数寄存器的程序：

```text
a7 = 1
 a0 = 'U'
 ecall

如果 ecall 后意外继续：
进入一个明显的失败停留位置
```

注意：第 08 课才真正实现 `putchar=1`。本课设置 `a7/a0` 只是为了 trap 后能看到“用户确实准备了这些寄存器”，不是为了让字符 U 已经打印出来。

### 第二步：把用户代码放进明确的链接区域

给这段代码独立输入 section，例如 `.text.user`，并导出：

```text
user_start
user_entry
user_end
```

链接脚本要明确收集它，不能依赖“也许某个 `.text.*` 通配刚好没丢”。

本阶段不复制用户代码到新物理页，直接执行它在最终 ELF 中的链接位置。第 21 课有分页后才会真正复制到进程私有映像。

### 第三步：画清楚三类栈

当前至少有：

```text
1. 管理/启动栈
   内核 rust_main 与管理逻辑使用

2. 用户栈
   U-mode 程序自己的 sp

3. 用户 trap 栈
   用户发生 trap 后，S-mode 入口立即切换到的可信内核栈
```

为用户栈和 trap 栈各静态预留一个明确范围，例如 16 KiB，并保持顶部 16 字节对齐。

它们可以放入受第 04 课 BSS 初始化覆盖的独立 section，但必须：

- 边界符号明确；
- 彼此不重叠；
- 不覆盖启动栈；
- Process 记录只保存真实范围，不伪造尚未分配的指针。

### 第四步：Process 在“需要时”才扩展

现在才给运行记录增加真正需要的内容，例如：

```text
user stack range
trap stack range
persistent user TrapFrame / context
```

这正是第 06 课不提前塞这些字段的原因。

### A 次验收

- [ ] 用户代码、入口和结束符号能从最终链接结果中找到。
- [ ] 用户栈、trap 栈、管理栈边界清楚且不重叠。
- [ ] 用户入口尚未执行，普通内核启动仍正常。
- [ ] 能解释为什么 trap 栈必须是内核可信资源，而不能继续使用任意用户 `sp`。

## B 次：只完成 `S-mode → U-mode`，先不关心回来以后怎么办

### `sret` 不是普通 `ret`

普通：

```text
call f
  ↓
ra 保存普通返回地址
  ↓
ret
```

特权级返回：

```text
S-mode 准备 sepc / sstatus
  ↓
sret
  ↓
CPU 按这些受控状态恢复执行模式和 PC
```

所以第一次进入用户态，需要内核自己构造可信状态，而不是让用户给一个任意 `sstatus`。

### 第一步：准备 `sepc`

`sepc` 指向：

```text
user_entry
```

它必须落在我们刚才验证过的用户代码范围内。

### 第二步：准备 `sstatus`

至少明确：

```text
SPP = 0
```

这样 `sret` 后进入 U-mode，而不是回到 S-mode。

本阶段不使用 S 模式中断：把 `sie` 中本课程可能用到的中断使能保持为 0，并显式设置本课所需的中断状态，不把 OpenSBI 留下的状态当隐含前提。

这里要特别记住：**只改 `sstatus.SIE` 不足以表达“用户运行期间不会出现某个 S 模式中断”**；具体中断源的 `sie` 使能也必须没有打开。第 13 课会反过来主动启用 timer。

### 第三步：准备 `sscratch`

返回用户前让 `sscratch` 保存可信 trap 栈顶部。

这样用户代码运行时：

```text
sp       = 用户栈
sscratch = 可信内核 trap 栈
```

### 第四步：恢复用户寄存器，最后恢复用户 sp

用户寄存器来自内核初始化好的持久现场：

```text
pc / sepc = user_entry
sp        = user_stack_top
其余寄存器 = 已知初值
```

用户 `sp` 最后恢复，因为在那之前汇编仍需要可信内核栈完成准备。

随后执行：

```text
sret
```

### 第五步：本阶段的受控风险边界

当前没有页表隔离。即使成功进入 U-mode，也只能证明：

```text
CPU 当前执行权限级别变成 U
```

不能证明：

```text
用户已经无法读写所有内核物理内存
用户已经无法接触设备
```

真实物理访问还受平台 PMP 配置影响；真正的进程页表隔离在第 21 课。

### B 次验收

因为用户马上会执行 `ecall`，最终现象仍要到 C 次才能证明模式切换。因此 B 次先检查构造事实：

- [ ] `sepc` 位于用户代码范围。
- [ ] 用户 `sp` 位于用户栈范围并 16 字节对齐。
- [ ] `sscratch` 指向可信 trap 栈顶部。
- [ ] `sstatus.SPP=0`。
- [ ] 用户现场不是从任意用户数据直接复制的特权状态。

## C 次：从 U-mode trap 回可信内核栈

这是本课最关键的一步。

### 为什么第一阶段 trap entry 不能直接复用

第 05 课的 trap 来自内核本身，当时：

```text
sp 已经是可信内核栈
```

但现在 trap 来自用户：

```text
sp 是用户控制/用户使用的栈
```

如果一进入 S-mode 就在当前 `sp` 上保存内核现场，相当于把最敏感的 trap 数据放到了用户栈里。

### 用 `sscratch` 交换栈

本课采用一个很适合教学的约定：返回用户前：

```text
sp       = user_sp
sscratch = trap_stack_top
```

用户来源 trap 的第一步用 CSR 交换：

```text
csrrw sp, sscratch, sp
```

交换后：

```text
sp       = 可信 trap_stack_top
sscratch = 原始 user_sp
```

这一条指令的价值在于：还没有借用普通临时寄存器，就先把不可信用户栈换走，并保留了原 user sp。

### 然后再保存 TrapFrame

在可信 trap 栈上分配 frame。

保存普通寄存器时仍遵守第 05 课规则：任何临时寄存器被借用前先保存。需要记录原用户 `sp` 时，从 `sscratch` 取得交换前的值，写入 `x2` 槽。

在调用 Rust 前，不允许默认信任用户留下的 `gp`、`tp` 等环境寄存器。如果当前内核编译/运行约定会依赖它们，必须从内核保存的可信环境恢复后再进入 Rust；不能因为这个受控样例“刚好没改”就把它写成通用假设。

### 内核处理期间切回内核故障入口

本课仍沿用“用户来源入口”和“内核自身故障入口”分开的教学设计。

用户 trap 已经切到可信栈并保存最小必要状态后，尽早把 `stvec` 切回第 05 课的内核故障入口。这样 Rust 处理过程中如果发生 S-mode 故障，不会被再次误判成普通用户请求。

这个早期汇编窗口保持尽可能短；本阶段关闭普通中断，也不声称已经支持嵌套 trap。

### 最后只报告，不返回

用户程序执行 `ecall` 后，Rust 报告：

```text
origin SPP = 0
scause exception code = 8
saved user sp ∈ user stack range
current trap frame ∈ trap stack range
sepc 位于用户代码中的 ecall
```

对于 RISC-V，U-mode `ecall` 的异常原因码为 8。实际能否由 S-mode 直接接收仍依赖固件的异常委派；如果被 M-mode/OpenSBI 接走，先核对委派和固件输出。

报告后稳定等待，不执行 `sret`。第 08 课再实现返回用户。

## 不要用错误证据证明“进入了 U-mode”

单独看到一个字母 `U` 没有证明力：内核自己也可以打印 U。

本课真正的证据组合是：

```text
sstatus.SPP 表明来源是 U
+
scause 表明是 U-mode ecall
+
sepc 位于用户程序
+
原始 sp 位于用户栈
+
处理 frame 位于可信 trap 栈
```

## 常见问题

| 现象 | 先检查 |
| --- | --- |
| `ecall` 原因不是 8 | `SPP`、真实执行模式、异常委派 |
| `sret` 后立刻取指 fault | `sepc`、用户代码链接地址、PMP/物理访问权限 |
| trap 后 Rust 马上异常 | trap 栈对齐、frame offset、可信 `gp/tp`/ABI 环境 |
| 保存的 x2 指向 trap 栈 | 是否忘了从 `sscratch` 记录原 user sp |
| 内核 fault 被当成用户 syscall | `stvec` 是否及时切回内核故障入口 |
| 用户无限循环后无法拿回 CPU | 本阶段没有定时抢占，属于已知限制 |
