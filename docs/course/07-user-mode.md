# 第 07 课：第一次进入用户态

状态：待开始。前置：[第 06 课](06-process.md) 和第一阶段真实实现完成。分 A、B 两次，每次 45～60 分钟。

## 目标与阅读

准备一个内嵌程序，在独立用户栈上进入 U 模式，再通过一次请求进入内核确认来源。此课请求后只报告并等待，第 08 课才返回用户程序。

阅读 OSTEP 第 6 章 Direct Execution，思考“允许直接执行指令，怎样保留内核控制权”。架构对照采用 [RISC-V Supervisor 规范](https://riscv.github.io/riscv-unified-db/manual/html/isa/isa_20240411/chapters/supervisor.html) 中 `sstatus`、`sscratch`、`sepc` 和返回指令的约定。

## A 次：先准备资源

时间：概念 10 分钟、代码与布局 30 分钟、检查 15 分钟。

1. 在计划中的 `src/user.S` 写一个短整数程序：准备 `a7=1`、`a0='U'`，执行 `ecall`，之后留一个受控停留循环。此时先不执行它。
2. 把代码放入专用输入段 `.text.user`，用链接脚本先于 `.text.*` 收集，并导出起止和入口符号；确认构建不会丢弃该段。使用最终链接位置执行，不复制代码到临时地址。
3. 静态预留独立用户栈与陷入内核时使用的栈，例如各 16 KiB，顶部保持 16 字节对齐；标清它们与原启动栈的范围，避免与 BSS 清零约定冲突。
4. 在进程记录中关联这些范围。原启动栈承担内核管理流程，用户栈承担用户代码，陷入栈承担用户请求期间的内核处理。
5. 初始化用户寄存器现场：入口、用户栈顶、已知初始寄存器值。不把内核栈内容当作用户现场。

## B 次：接住用户发出的第一次请求

时间：栈切换设计 15 分钟、接入 25 分钟、观察复盘 20 分钟。

第一阶段入口直接在当前 `sp` 上保存现场；从用户态进入时不能沿用这个假设。本课选择分开的用户来源入口和内核故障入口。

1. 内核执行期间保留第一阶段的内核故障入口。返回用户前安装用户来源入口，并通过 `sscratch` 准备可信陷入栈信息。
2. 用户入口首先换到可信内核栈，保存全部整数现场，包括原用户 `sp`；再调用 Rust。临时寄存器必须先保存后借用。若 Rust 运行依赖内核 `gp`、`tp`，须从可信元数据恢复，不能沿用用户值。
3. 进入 Rust 前把异常入口切回内核故障入口，避免内核处理期间的故障被当作第二次用户请求。栈切换到入口切换之间的汇编窗口要保持最小，所用地址必须已验证。
4. 为首次进入用户构造返回状态：`sepc` 指向入口，`sstatus.SPP=0`，恢复用户整数寄存器并执行 `sret`。状态来自内核构造，不由用户任意指定。
5. 本阶段不启用中断源，显式将 `sie` 清零；不能仅清除 `sstatus.SIE` 就推断用户运行期间没有 S 模式中断。
6. 用户执行 `ecall` 后报告保存现场：来源 `SPP=0`、异常原因 8、保存的 `sp` 在用户栈范围内，当前处理栈在内核陷入栈范围内。

上述寄存器行为依据 [RISC-V Supervisor 规范](https://riscv.github.io/riscv-unified-db/manual/html/isa/isa_20240411/chapters/supervisor.html)。QEMU/OpenSBI 的实际委派与物理访问权限要在实验中确认；若固件拦截或用户取指失败，先记录固件版本和异常报告再排查。

## 预期与常见问题

预期先输出内核初始化信息，再出现一次用户来源请求报告，随后等待。单独打印字母 U 不作为特权级验证。

| 现象 | 先检查 |
| --- | --- |
| `ecall` 原因不是 8 | 是否真的进入 U 模式，保存的 SPP 是什么 |
| 进入后立即取指错误 | 用户入口是否在有效代码范围，固件物理权限是否允许 |
| 调用 Rust 后异常 | 内核栈对齐、寄存器保存及内核运行环境是否正确 |
| 保存的 `sp` 指向内核栈 | 是否把切换后的栈误记成用户原始栈 |

## 验收

- [ ] 三类栈范围清楚且不重叠，用户代码有明确边界。
- [ ] 用户来源 `ecall` 报告证明已进入 U 模式。
- [ ] 处理发生在可信内核栈，内核故障仍有独立诊断路径。
- [ ] 能解释“独立栈”不等于“地址空间已隔离”。
- [ ] 原启动检查通过，另记本课报告到 [进度记录](progress.md)。
