# 第 04 课：给内核画一张内存地图

状态：待开始。前置：[第 03 课](03-panic.md) 验收完成。拆成 A、B 两次，每次 45～60 分钟。

## 为什么在 trap 之前先学内存布局

下一课要在异常发生时把寄存器保存到栈上。如果连“代码、数据、BSS、启动栈分别在哪里”都说不清，trap 一出问题就很难判断到底是入口错、栈错，还是写坏了别的内存。

所以本课只解决两个问题：

1. **当前内核的主要区域实际放在哪里？**
2. **Rust 代码开始运行前，谁保证普通 BSS 是零？**

分页、虚拟地址空间和页表还没有开始；本课观察的是当前裸机内核的实际链接布局。

## 本课新词

| 名称 | 先这样理解 |
| --- | --- |
| section / 段 | ELF 中把相似用途内容分组的区域 |
| linker symbol | 链接器放在某个地址上的“位置标记” |
| BSS | 运行时需要空间、初始值按约定为零的可写静态区域 |
| `NOLOAD` / `NOBITS` | 文件里不必真的存一大串零，只记录运行时需要这块空间 |

不要把“链接符号”理解成一个普通 Rust 变量。它最重要的信息通常是**符号所在地址**。

## A 次：先把地图画出来，不改启动初始化

### 第一步：对照现有链接脚本

打开 [linker.ld](../../linker.ld)，再打开 [src/main.rs](../../src/main.rs) 中的启动栈声明。

先画出当前逻辑顺序：

```text
0x80200000 附近
┌────────────────────┐
│ .text              │ 机器指令
├────────────────────┤
│ .rodata            │ 只读数据
├────────────────────┤
│ .data              │ 有初值的可写数据
├────────────────────┤
│ .bss / .bss.*      │ 零初始化静态数据 + 当前启动栈输入段
└────────────────────┘
```

现在的问题是：如果以后我们想“清零普通 BSS”，不应该靠模糊的通配范围去猜当前正在使用的启动栈是否也在里面。

### 第二步：给每个重要区域加边界

在链接脚本中为区域增加开始/结束标记，例如：

```text
stext      / etext
srodata    / erodata
sdata      / edata
sboot_stack/ eboot_stack
sbss       / ebss
```

名称不是行业强制标准，但一旦课程选定，就保持一致。

把 `.bss.stack` 明确收进独立的启动栈输出区域，例如 `.boot_stack (NOLOAD)`；普通 `.bss` 再单独收集。目标不是“段越多越专业”，而是建立一个明确不变量：

```text
[sbss, ebss)       = 本课允许主动清零的普通 BSS
[sboot_stack, eboot_stack) = 启动栈，不属于普通 BSS 清零范围
```

输入 section 一旦已经被前面的输出 section 收集，不应再靠后面的通配规则重新解释。修改后务必查看最终地址结果，而不是只相信脚本文字。

### 第三步：在 Rust 中打印边界地址

创建计划中的 `src/memory.rs`，通过外部符号声明取得这些链接器标记。

本项目使用 Rust 2024 edition；外部块按当前语法写成 `unsafe extern "C"`。这里的符号代表链接地址，不是“存着某个整数的普通变量”。

用第 02 课的输出工具打印：

```text
.text       [start, end)
.rodata     [start, end)
.data       [start, end)
.boot_stack [start, end)
.bss        [start, end)
```

注意统一使用**半开区间** `[start, end)`：

```text
start 属于区域
end   是第一个不属于区域的地址
大小  = end - start
```

这会让后面的清零、页映射和越界检查全部更清楚。

### 第四步：做地图不变量检查

至少核对：

- 每个 `start <= end`；
- 相邻区域没有意外重叠；
- `eboot_stack - sboot_stack == 65536`；
- 普通 BSS 与启动栈不重叠；
- `_start` 地址位于 `.text` 范围内；
- 当前 `sp` 在启动栈范围附近并符合“从高地址向低地址使用”的规划。

链接脚本不是 Rust 源文件，Cargo 不一定总能把它的内容变化当成普通源码依赖。如果修改后怀疑没有重新链接，可先显式触发重建，例如 `cargo clean && cargo build`，再观察结果；不要拿旧 ELF 的地址做结论。

## B 次：明确谁保证 BSS 为零

### 先问一个关键问题

Rust 里写一个零初始化静态数据时，代码会默认它在程序可见前具有正确初值。

当前 QEMU/ELF 加载路径往往已经会让 NOBITS/BSS 内存呈现为零，但教学内核不应该把“这次加载器刚好给了零”当作自己永远无需理解的启动契约。

本课要实现并验证：

```text
_start
  ↓ 准备最早期执行环境
清零普通 [sbss, ebss)
  ↓
call rust_main
```

### 清零算法先写成普通语言

```text
cursor = sbss
end = ebss

while cursor < end:
    *cursor = 0
    cursor += 1
```

这是按字节清零的教学版本，容易验证边界；现在不追求最快。

实现时：

1. 用 `la` 取得 `sbss` 和 `ebss`。
2. 空区间直接结束。
3. 每次只写 `[sbss, ebss)` 内地址。
4. 绝不能写到 `ebss` 本身。
5. 不调用 Rust 函数来完成“Rust 运行前”的最早期初始化。
6. 启动栈已经独立，不让普通 BSS 清零规则碰它。

### 必须证明“清零代码真的工作”

只打印一个本来就是 0 的变量不能证明任何事，因为加载器可能已经给了零。

更可靠的教学探针是：在普通 BSS 中明确预留一个 8 字节区域，并导出它的符号，例如用独立汇编输入段：

```text
.bss.probe
  ↓
bss_probe: 8 bytes
```

测试流程：

```text
进入清零循环前
  ↓
把 probe 写成明确的非零模式
  ↓
执行 [sbss, ebss) 清零
  ↓
进入 Rust
  ↓
通过原始指针/volatile 读取 probe
```

预期：

- 开启清零 → probe 为 0；
- 临时跳过清零 → probe 保留刚写入的非零模式；
- 恢复清零并移除测试填充 → 正常启动。

使用原始/volatile 读取是为了明确观察汇编在 Rust 之前对那块内存做出的真实修改，不创建长期存活的 `static mut` 可变引用。

### 为什么先设置 `sp` 再清普通 BSS 仍可以

本课的清零循环只使用寄存器，不依赖 Rust 调用栈；而启动栈已经从普通 BSS 范围排除。

因此：

```text
sp 指向高地址栈顶
```

和：

```text
cursor 从低地址向高地址清 BSS
```

并不矛盾。这两个“方向”描述的是完全不同的操作。

## 常见问题

| 现象 | 先检查 |
| --- | --- |
| 新布局后连 `_start` 都没运行 | `ENTRY(_start)` 和 `.text.entry` 是否仍正确收集 |
| 清零后启动崩溃 | `[sbss,ebss)` 是否误覆盖栈、代码或链接元数据 |
| 边界打印像很小的普通数字 | 是否读取了边界地址处的内容，而不是取得符号地址 |
| probe 永远是 0 | 是否真的在清零前写入非零、是否运行的是新 ELF |
| 修改 linker.ld 后地址完全没变化 | 是否重新链接，而不是复用了旧构建产物 |
