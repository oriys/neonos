# 第 01 课：从开机到 Hello kernel

状态：待开始。预计 45～60 分钟。前置：能打开项目文件并在项目根目录使用终端；无需提前掌握汇编。见 [第一阶段安排](stage-01.md)。

## 今天的目标

完成后，你能在终端看到自己增加的欢迎语，并说明：谁启动了谁、Rust 为什么没有普通 `main`、字符怎样到达终端。

预习：从 [OSTEP 官网](https://pages.cs.wisc.edu/~remzi/OSTEP/) 打开第 2 章 Introduction，先了解操作系统管理资源的动机即可。

## 先认识 5 个角色（10 分钟）

把这次启动理解为一次接力：

```text
QEMU 模拟的 RISC-V 机器
  → OpenSBI 固件
  → _start：准备栈
  → rust_main：执行 Rust 代码
  → 向 UART 写字符：终端显示 Hello kernel
```

- QEMU：在你的电脑上模拟我们实验需要的机器。
- OpenSBI：在当前项目配置中，先运行的固件，然后把控制权交给内核。
- `_start`：项目定义的内核入口。
- 栈：函数运行时需要的一块工作空间，本课先理解用途。
- UART：串口设备；本项目通过它向终端输出字符。

## 对照文件找路线（10 分钟）

按顺序打开：

1. [Cargo 配置](../../.cargo/config.toml)：找编译目标和 QEMU 启动参数。
2. [链接脚本](../../linker.ld)：只找 `ENTRY(_start)` 和 `0x80200000`。
3. [内核入口](../../src/main.rs)：依次找 `_start`、`la sp`、`call rust_main`、`rust_main` 和 `UART`。

`no_std` 表示不依赖 Rust 标准库；`no_main` 表示不用普通应用的启动入口。这里由我们自己的 `_start` 接过控制权。

先回答：输出问候语的循环发生在准备栈之前还是之后？如果文字打印完了，程序接下来去哪？

## 动手实验（20 分钟）

在项目根目录运行：

```sh
cargo run
```

预期：启动信息之后出现 `Hello kernel`，随后等待。退出 QEMU：先按 `Ctrl-A`，松开，再按 `X`。

如果命令失败，先记录第一条错误并解决环境问题，不急着改源码。仓库此前的实现计划记载了环境安装步骤，但仍以本机实际运行结果为准。

在 `rust_main` 的字节字符串中保留原问候语，增加第二行，例如：

```rust
b"Hello kernel\nWelcome to neonos!\n"
```

这是替换原循环里的字节字符串，不是把这段单独加到函数末尾。先猜一下 `\n` 会产生什么效果，再运行观察。当前练习使用 ASCII 字符，避免把编码和终端显示问题混入第一课。

然后运行已有的启动检查：

```sh
./tests/boot.sh
```

它应当成功退出，因为我们保留了它检查的 `Hello kernel`。新欢迎语需要你另外观察确认；现有脚本不会验证新增的那一行。

## 常见问题

| 现象 | 先检查 |
| --- | --- |
| 找不到 Cargo 或 QEMU | 开发工具是否已安装，终端是否能找到它们 |
| 提示目标所需的 `core` 不存在 | 是否已安装项目配置中的 RISC-V 编译目标 |
| 只有 OpenSBI 输出 | 编译是否成功、入口和串口输出代码是否被误改 |
| 输出后不退出 | 当前 `halt()` 会一直等待，这是预期行为 |
| 改欢迎语后启动检查失败 | 是否保留了检查脚本需要的 `Hello kernel` |
