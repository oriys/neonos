# 第 32 课：拿不到锁，就先让 CPU 做别的事

状态：待开始。前置：[第 31 课](31-atomics.md)。分 A、B 两次，每次 45～60 分钟。

## 目标与设计

实现由内核管理、用户线程通过句柄使用的非递归互斥锁。内核内部元数据仍由短不可抢占区间保护；不在中断处理器调用睡眠锁接口。

## A 次：获取与等待

1. 固定对象表记录所属进程、代际、所有者 TID 和 FIFO 等待队列。先实现无竞争 lock/unlock，检查非所有者释放和重复加锁。
2. 已被其他线程持有时，在同一临界区登记等待并标记 Blocked；不可先回调度器再登记。
3. unlock 采用明确交接：若有等待者，所有权直接赋给队首，并设置该线程的“已获锁待返回”状态，然后只唤醒一次；否则置空。
4. 恢复时识别已交接状态、消费一次并完成原调用，不从头执行普通 lock 后把自己当成递归持锁者。
5. 用户两线程对共享计数执行多次“lock→读改写→unlock”，最终计数准确。

## B 次：边界与回收

1. 在线程持锁期间插入可控抢占，验证等待者 Blocked 而非无限运行，持锁者仍有机会继续。
2. 重复 lock 返回 -9，非所有者 unlock 返回 -10。句柄销毁只允许空闲、无等待者且无条件变量绑定；其他情况返回 -9。
3. FIFO 只保证交接顺序，不等于严格实时响应，也不解决优先级反转；把不同优先级场景作为观察而非性能承诺。
4. 持锁线程退出或故障按阶段政策结束整个进程，取消等待与交接，再回收对象；不能把保护中的数据视为仍完整。

## 常见问题与验收

| 现象 | 先检查 |
| --- | --- |
| 被唤醒后再次阻塞 | 是否丢失所有权交接的完成阶段 |
| 一个线程被入队多次 | 重试是否重复登记同一等待者 |
| 销毁后旧句柄还能用 | 是否验证对象代际 |

- [ ] 计数正确，所有者唯一，FIFO 交接轨迹可核对。
- [ ] 无竞争、竞争、非法调用和对象容量满均有结果。
- [ ] 退出清理没有悬挂等待者，更新 [进度记录](progress.md)。

小练习：说明“被唤醒”和“已经获得锁”在不同锁设计中为什么不一定是一回事。
