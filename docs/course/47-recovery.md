# 第 47 课：重启以后，怎样把已提交事务恢复完整

状态：待开始。前置：[第 46 课](46-journal.md)。分 A、B、C 三次，每次 45～60 分钟。

## 目标

在挂载普通文件系统之前检查日志：未提交事务丢弃，已提交事务完整重放，再清空日志。随后把故障注入扩展到事务的每个持久化边界，验证恢复结果和幂等性。

## A 次：启动恢复

恢复顺序：

```text
读取并校验日志头
  ↓
empty        → 继续挂载
uncommitted  → 清理/忽略后继续挂载
committed    → 校验全部 payload
  ↓
按目标块号把完整 payload 重放到 home blocks
  ↓
flush
  ↓
清空日志头并 flush
  ↓
运行必要的一致性检查后挂载
```

1. 日志头、目标块号或 payload 校验失败时，拒绝自动重放，进入只读诊断；不能拿损坏日志覆盖正常文件系统。
2. 目标块必须属于该事务允许修改的文件系统区域，不能通过坏日志写到超级块外、设备尾部或任意宿主机范围。
3. committed 事务无论 home block 已安装 0 个、部分还是全部，都重放完整集合。
4. 重放相同的新块内容两次得到相同结果，因此恢复可重复执行。
5. 恢复完成后再清日志；不能先清日志再安装，否则恢复途中再次崩溃会失去唯一提交副本。

## B 次：故障矩阵

增加 `tests/crash-recovery.sh`，每个案例都从同一已知正确基线副本开始，并在以下明确持久边界终止 QEMU：

| 故障点 | 磁盘上可能看到 | 重启期望 |
| --- | --- | --- |
| FP1 payload/header flush 前 | 日志不完整 | 不提交；旧状态保持 |
| FP2 日志内容 flush 后、commit 前 | 完整未提交日志 | 丢弃事务；旧状态保持 |
| FP3 commit 写后、commit flush 前 | commit 是否持久未知 | 只按重启后实际磁盘状态判断 |
| FP4 commit flush 后、安装前 | committed + 旧 home | 重放，得到新状态 |
| FP5 部分 home 安装后 | committed + 新旧混合 home | 完整重放，得到新状态 |
| FP6 home 全部 flush 后、清日志前 | committed + 新 home | 再重放仍得到同一新状态 |
| FP7 清日志写后、最终 flush 前 | home 已是新状态，日志是否清空未知 | 无论日志是否仍 committed 都应恢复到同一新状态 |

FP3 和 FP7 的重点是：测试不能预设一次普通写请求已经持久。重启后先观察磁盘上 commit/log 实际状态，再按协议判定。

每个故障案例恢复后运行：

```text
fsck
目标文件内容检查
位图/inode 计数检查
旧 storage 回归
```

## C 次：幂等与课程总验收

1. 对 FP4、FP5、FP6 恢复后的同一镜像再执行一次恢复启动；第二次不应改变文件内容、位图、inode 或日志状态。
2. 故意让“重放完成但清日志前”再次终止，第三次启动仍应正确。
3. 连续执行多轮小事务，每轮正常 sync 后运行 fsck，确认日志块不会被普通分配器使用。
4. 再跑 shell、fork/exec、线程、文件接口和磁盘程序测试，确认日志没有破坏前面阶段的行为。
5. 在课程记录中写出当前保证边界：哪些操作经过日志、哪些只依赖 ordered data、哪些仍不具备崩溃原子性。

## 常见问题

| 现象 | 先检查 |
| --- | --- |
| commit 后崩溃恢复成旧状态 | 恢复是否把 committed 日志误当作缓存垃圾 |
| 恢复一次成功、第二次损坏 | 重放是否包含非幂等副作用或先清日志 |
| fsck 通过但文件内容是旧的 | 本事务的数据块是否属于日志/ordered-data 保证范围 |
| 故障矩阵结果偶尔变化 | 是否在非 flush 边界 kill，或测试复用了上一个工作镜像 |
