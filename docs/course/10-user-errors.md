# 第 10 课：用户程序出错，不等于内核出错

状态：待开始。前置：[第 09 课](09-exit.md) 验收完成。分 A、B 两次，每次 45～60 分钟。

## 目标与阅读

用户程序发生受控异常后，内核记录失败并运行下一个程序；内核自身故障仍报告并停止。回看 OSTEP 第 6 章的控制权问题，复盘第五课的异常入口与第三课的 panic。

这里的“用户错误可结束”仅指已知受控异常路径。当前没有内存隔离和定时抢占，不能承诺任意用户程序都不会损坏或卡住内核。

## A 次：给错误分流

时间：分类 15 分钟、接入 25 分钟、对照实验 15 分钟。

| 来源与事件 | 本阶段处理 |
| --- | --- |
| U 模式 `ecall`，合法调用 | 交给分发器，返回或退出 |
| U 模式 `ecall`，未知号或非法参数 | 返回协议错误码 |
| U 模式非法指令等受控同步异常 | 记录 `Faulted`、原因和地址，结束当前实例 |
| S 模式异常或内核 panic | 报告内核故障并停住 |
| 未预期的中断 | 报告并排查配置，不能伪装成普通用户错误 |

1. 分类依据是保存的来源状态和原因，不能因为存在“当前进程”就把所有错误算到用户头上。
2. 在用户代码内放置带标签的 `.4byte 0` 非法编码，不用 Rust 非法指针访问制造测试。
3. 错误处理保留运行编号、程序名、`scause`、`sepc`、`stval`，通过第 09 课结束路径回到管理流程。不要对未知异常随意前移 `sepc` 再返回。
4. 先运行错误程序，再运行正常打印并退出的程序，确认管理流程继续且旧错误状态已清理。
5. 单独运行内核故障实验，确认仍报告并停住。这个场景不能与期望完成的批次混在一起；完成后移除临时内核故障触发点。

## B 次：整理接口与检查脚本

时间：用户封装 20 分钟、场景检查 25 分钟、复盘 15 分钟。

1. 创建计划中的 `src/user_api.S`，把 `putchar` 和 `exit` 请求包装成可调用的汇编函数，用户程序通过这些符号调用，不再每处重复编号。
2. 明确用户入口不是普通内核 `call`：最外层没有可用的内核返回地址，程序结束必须显式退出。若增加用户启动包装，它负责在用户主函数返回后发出有效退出请求。
3. 保持用户封装只使用整数、用户栈和 `ecall`，不直接调用内核输出函数。独立编译的 Rust 用户库属于后续扩展，本课先让最小汇编接口一致可用。
4. 增加阶段检查脚本 `tests/user.sh`，沿用已有启动脚本的进程清理和超时方式；检查完整完成标记及各场景顺序、次数，遇到失败标记或意外 panic 应失败。
5. 把预期内核故障作为单独运行模式或单独构建场景，分别检查“错误报告出现”与“不出现后续成功标记”。不要用原启动脚本的 Hello 匹配充当全部验证。

所有演示程序与检查模式要有明确选择方式，避免靠人工记住哪个触发语句被注释。实现时选择一种简单的构建开关或固定测试批次，并在脚本说明里写清。

## 总验收清单

- [ ] 用户正常打印并返回，错误请求得到 -1 或 -2。
- [ ] 合法退出码被记录，退出后回到内核管理流程。
- [ ] 用户非法指令产生 `Faulted`，随后正常程序仍能完成。
- [ ] 内核故障单独报告停住，不被记为用户退出。
- [ ] 用户接口约定统一，100 次运行完成且无状态残留。
- [ ] 原启动检查和新阶段检查分别通过，记录真实操作与结果。
- [ ] 能画出用户请求、内核处理、返回用户或结束实例的完整路线。

常见问题：若正常程序被前一个错误程序影响，先检查实例重置和栈回收；若出现错误报告但脚本成功，先检查是否过早匹配 Hello 或完成标记；若内核故障也继续运行，先检查分类是否丢失来源状态。

小练习：解释为什么未知系统调用适合返回错误，而非法指令在当前实现中适合结束程序。
