# 第 09 课：程序退出后，内核继续做什么

状态：待开始。前置：[第 08 课](08-syscalls.md) 验收完成。分 A、B 两次，每次 45～60 分钟。

## 目标与阅读

用户执行 `exit(7)` 后不会返回，内核记录退出码并继续启动下一个程序。阅读 OSTEP 第 4～5 章关于生命周期和退出的内容；父子进程、`wait` 与 `fork` 留到后续阶段。

本课沿用一个固定进程槽位，以顺序运行理解资源生命周期。没有定时抢占，也没有进程间切换队列。

## A 次：建立清楚的内核继续点

时间：生命周期 15 分钟、汇编桥接 25 分钟、验证 15 分钟。

此前请求后总回到用户。本课增加一条明确的结束路径：

```text
内核管理函数
  → 保存内核继续点 → 进入用户
  → 用户请求 exit → 内核记录 Exited(7)
  → 恢复内核继续点 → 管理函数拿到退出结果
```

1. 为运行入口设计 `run_user` 汇编桥接，保存内核调用约定要求的 `ra`、`sp`、被调用者保存寄存器，以及实现依赖的其他状态，形成独立的 `KernelContext`。
2. `KernelContext` 位于生命周期覆盖整次运行的可信存储，不能指向会被退出流程重置的用户栈或陷入栈。它和用户 `TrapFrame` 分工不同。
3. `exit` 按协议检查退出码，合法则更新当前记录并选择“结束进程”；不再调整现场后返回用户。非法值返回 -2，照常恢复用户。
4. 汇编结束路径先恢复内核故障入口等运行约定，再恢复保存的内核继续点。管理流程收到结束结果，打印 `kernel resumed: exit=7`。
5. 这个桥接不是从任意 Rust 调用栈随意跳回，也不是 Rust 的异常展开：入口与结束出口都由汇编成对设计，跨越期间不持有依赖 `Drop` 释放的资源或长期可变借用。

固定退出结果通过清楚的返回值或可信记录传给管理者。不要仅跳到一个新 Rust 函数地址便声称原管理函数已恢复。

## B 次：顺序运行与回收

时间：资源清单 10 分钟、重复运行 25 分钟、错误路径和复盘 20 分钟。

1. 用户程序在 `exit(7)` 后放置可识别的错误标记路径；正确实现永远不会到达它。
2. 管理流程重新取得控制权后，再清理用户记录、用户栈和陷入栈；不可在仍使用陷入栈时把它清零。
3. 新实例重新设置入口、寄存器、退出信息和运行编号，避免上一次的返回值或错误状态残留。
4. 顺序执行程序 A 和程序 B，记录 A 退出后 B 才启动。
5. 再重复运行同一个短程序 100 次，检查完成计数、各次栈地址和最终标记。固定栈可复用，但不能让保存现场不断堆叠。

## 验收与常见问题

| 场景或现象 | 预期或排查 |
| --- | --- |
| `exit(7)` | 记录退出码 7，出现内核继续标记，用户退出后路径不可达 |
| `exit(256)` 后正常输出 | 返回 -2，当前程序仍在运行 |
| 第二次运行立即退出 | 新实例的入口、现场和退出状态是否全部重置 |
| 每次运行栈地址下降 | 是否一直增加陷入帧，没有恢复内核继续点 |
| 退出瞬间内核异常 | 是否过早清零仍在使用的栈，或漏恢复关键寄存器 |
