# 第 34 课：一次允许几个线程进入

状态：待开始。前置：[第 33 课](33-condvar.md)。分 A、B 两次，每次 45～60 分钟。

## 目标与阅读

阅读 OSTEP 第 31 章。理解信号量计数保存可用许可，互斥锁保存所有者；信号量可以由不同线程执行 post，不能套用锁的所有者检查。

## A 次：许可与交接

1. 对象表记录 count、max 和 FIFO 等待者。sem_wait 有许可就减一返回，否则无副作用登记等待。
2. post 若有等待者，直接交付一个许可并记录其调用完成状态；否则增加 count。不要既增加 count 又给等待者预留同一个许可。
3. 线程恢复消费一次完成状态，不再次减 count。检查 initial/max 非法和计数上溢。
4. 用 max=2 让三个工作线程申请资源；共享活跃计数的更新也必须有同步保护，记录最大活跃值不超过 2。
5. 这个资源池实验要求每次成功 wait 都有一次 post；普通信号量 API 本身不会自动判断业务是否忘记归还许可。

## B 次：用信号量重写有界队列

1. 容量 N，empty 初始 N、full 初始 0，两者 max=N；另用第 32 课互斥锁保护队列字段。
2. 生产者先 wait(empty)，再锁队列并入队，解锁后 post(full)；消费者先 wait(full)，再出队，最后 post(empty)。
3. 不得持队列锁阻塞等待 empty/full，否则另一方可能无法改变条件。
4. 输入总量固定，输出检查复用第 33 课。空满许可加在途操作才构成完整守恒，不能在任意中途时刻断言 empty+full=N。
5. 比较条件变量版本：指出谁保存谓词、谁保存许可、哪一步避免重复消费。

## 常见问题与验收

| 现象 | 先检查 |
| --- | --- |
| 同一许可让两个线程通过 | post 是否计数和交接双重记账 |
| 队列空时全体卡住 | 是否拿着队列锁等待 full |
| 活跃统计有时超过限制 | 许可算法或统计计数本身是否存在竞争 |

- [ ] 容量边界、FIFO 交接、非法参数与溢出正确。
- [ ] 活跃上限与队列内容守恒可验证。
- [ ] 对象无等待者和待交接引用后可销毁，更新 [进度记录](progress.md)。
