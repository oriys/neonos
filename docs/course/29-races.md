# 第 29 课：两个加一，为什么可能只加了一次

状态：待开始。前置：[第五阶段](stage-05.md)。预计 45～60 分钟。

## 目标与阅读

阅读 OSTEP 第 26 章。把共享计数更新拆成读取、计算和写回，观察操作交错。Rust 的数据竞争是未定义行为，逻辑竞争则可以出现在合法原子访问之间，参考 [Rustonomicon：Races](https://doc.rust-lang.org/nomicon/races.html)。

## 先手排顺序（10 分钟）

计数初值 0：A 读到 0，B 读到 0，A 写回 1，B 写回 1。两次逻辑加一，最终却是 1。单核一次执行一条路线，也能在多条指令之间切换。

## 宿主机确定性实验（30 分钟）

1. 计划创建独立的 `experiments/races.rs`，使用宿主机 Rust 标准库，不使用仓库裸机 Cargo 默认目标；可通过 `rustc --edition=2024` 显式编译该单文件。
2. 用 `Arc<AtomicUsize>` 保存计数，两个线程各做一次 load 后等待同一个两方 Barrier，再分别 store(旧值+1)。这保证两次读取都在写入之前。
3. 主线程 join 两者后检查结果是 1；先用 SeqCst 简化推理，说明最强排序也不会把两次独立访问合成一次更新。
4. 改用原子 `fetch_add`，在操作前对齐起跑即可，预期是 2。不要保留阻止修复算法推进的错误屏障位置。
5. 另用单线程交错模拟画出每一步，作为 neonos 线程尚未实现时的教学依据。

本课不使用未同步的 Rust 普通变量、`static mut` 或 `volatile` 冒充合法并发实验，也不认为 `yield_now()` 或 sleep 能保证所需先后顺序。

## 常见问题与验收（10 分钟）

| 现象 | 先检查 |
| --- | --- |
| 有时 1 有时 2 | 两次 load 后是否有真正的同步屏障 |
| 改为原子仍是 1 | 是否仍使用分开的 load 与 store |
| 程序一直等 | Barrier 人数是否匹配实际参与者 |
