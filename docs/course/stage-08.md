## 本阶段采用的教学日志模型

为了把重点放在“为什么日志能恢复”，第一版采用固定容量的**物理 redo log**：日志记录将来要覆盖的文件系统块号和这些块的完整 4 KiB 新内容。一次事务最多修改有限个块，超出日志容量时操作在开始持久化前失败。

提交顺序固定为：

```text
准备新数据/元数据
  ↓
把事务内容写入日志区
  ↓
flush：确保日志内容持久
  ↓
写 commit 记录
  ↓
flush：commit 持久后事务才算已提交
  ↓
把日志中的块安装到 home location
  ↓
flush
  ↓
清除日志头
  ↓
flush
```

恢复只信任格式合法且 commit 完整的事务。未提交日志不安装；已提交但尚未安装完的事务按日志完整重放。因为重放写入的是相同块的相同新内容，所以设计成幂等。

### 数据写入边界

第一版不是通用数据库事务。对于“扩展普通文件”这种操作，先把新文件数据块写到其最终数据位置并 flush，再提交只覆盖元数据更新的日志事务。这样日志提交后，元数据不会指向尚未保证持久的数据。覆盖已有文件数据、目录操作和其他语义必须在教材中明确其日志覆盖范围，不能笼统宣称所有 write 都具有完整 POSIX 崩溃原子性。

## 故障模型

测试脚本只在代码显式的持久化边界终止 QEMU，例如：

```text
FP1 日志内容 flush 前
FP2 日志内容 flush 后、commit 前
FP3 commit 写入后、commit flush 前
FP4 commit flush 后、安装 home block 前
FP5 安装部分 home block 后
FP6 home block 全部 flush 后、清日志前
FP7 清日志后、最终 flush 前
```

“在某行 Rust 代码后 kill QEMU”并不自动等于那之前的磁盘写都已持久。只有设备完成与 flush 语义定义的边界才作为本课程故障点。

## 计划产物

按实际目录复用已有模块，计划加入：

- `docs/fs-log-format.md`：日志块布局、事务容量、状态和端序。
- `tools/fsck.py`：只读离线检查器，默认不修复。
- `src/fs/journal.rs` 或等价模块：日志提交与恢复。
- `tests/crash-recovery.sh`：创建基线镜像、复制、故障注入、重启、fsck 与内容核对。

检查器和内核必须共享同一份格式约定，但不要让检查器只调用内核实现后自证正确；宿主机工具独立解码磁盘字节更容易发现格式不一致。

## 总验收

- [ ] 能解释“系统调用成功返回”“设备完成”“flush 完成”“事务 commit”是四个不同概念。
- [ ] 至少一个无日志故障场景可以稳定产生并解释元数据矛盾。
- [ ] fsck 对正常镜像零报错，对构造坏镜像指出具体对象和规则。
- [ ] 未提交日志不会被恢复为已提交状态。
- [ ] 已提交事务在任一安装中断点后都能通过重放恢复。
- [ ] 恢复是幂等的：同一镜像连续执行恢复两次，第二次不改变文件系统内容。
- [ ] 恢复后重新运行 fsck、文件内容检查、shell/文件接口和旧 storage 测试。
- [ ] 文档明确写出本日志不保证的操作和真实断电限制。

完成第八阶段后，第一轮课程闭环：内核不仅能创建持久文件，还能在课程定义的崩溃模型下识别和恢复已提交事务的一致状态。
