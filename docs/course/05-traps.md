# 第 05 课：捕获第一次 CPU 异常

状态：待开始。前置：[第 04 课](04-memory-layout.md) 验收完成。建议拆成 A、B、C 三次，每次 45～60 分钟。

## 为什么这课是第一阶段的终点

第 03 课只能处理 Rust 主动 `panic!`。但 CPU 还可能因为非法指令、坏地址、系统调用或中断改变正常执行路线。

本课只做最小版本：

```text
内核正常运行
  ↓
CPU 遇到一次受控非法指令
  ↓
按照 stvec 跳到我们的汇编入口
  ↓
保存整数现场和关键 CSR
  ↓
进入 Rust 打印诊断
  ↓
停住
```

**本课不恢复执行。** `sret`、用户态、系统调用返回、定时器都属于后面的课。先把“能可靠接住并解释一次异常”做对。

## A 次：先理解 CPU 会留下哪些线索

### exception 和 interrupt 先分开

本课程把 trap 当作“处理器把控制权交给特殊入口”的总称。里面至少分：

```text
同步异常 exception
  例：非法指令、ecall
  和当前执行的指令直接相关

中断 interrupt
  例：定时器
  由外部/异步事件请求处理
```

本课只主动制造**同步非法指令异常**。普通中断源继续关闭。

### 认识 5 个状态概念

CSR 可以先理解为 CPU 提供的一组控制/状态寄存器。

| 名称 | 本课用途 |
| --- | --- |
| `stvec` | S 模式 trap 入口地址和模式 |
| `sepc` | trap 相关的指令地址 |
| `scause` | 中断/异常标记和原因编号 |
| `stval` | 与 trap 相关的辅助值；可能为 0 |
| `sstatus` | 保存/控制 S 模式的一部分状态，后续会继续使用 |

阅读 [RISC-V Supervisor 规范](https://docs.riscv.org/reference/isa/priv/supervisor.html) 时只查这几个名字，不通读整份规范。

### Direct 模式先这样理解

本课把 `stvec` 配成 Direct 模式：所有 S 模式可见 trap 都先进入同一个入口。

入口地址需要满足规范对齐，写入 `stvec` 时低模式位保持 Direct 所需的 0。不要把一个普通 Rust 函数地址直接塞进去就算完成，因为 CPU 进入 trap 时**不会自动替普通函数调用保存全部寄存器、准备参数和 Rust 所需调用环境**。

### 为什么这次明明不返回，还要保存完整整数现场

如果只为了打印 `scause`，当然可以写一个更短的临时入口。但第 07～14 课很快就要真正恢复用户现场和做任务切换。

所以本课有意建立一个未来能扩展的整数 `TrapFrame`：

```text
32 个整数寄存器槽位
+ sstatus
+ sepc
+ scause
+ stval
= 36 × 8 bytes
= 288 bytes (RV64)
```

其中：

- `x0` 槽固定记 0，方便“寄存器编号 = 槽位编号”；
- `x2` 是 `sp`，要保存**trap 发生时原来的 sp**，不是分配 TrapFrame 之后的新 sp；
- 当前课程不使用浮点/向量状态，因此本课不声称保存 F/V 扩展上下文。

### 先在纸上画 frame，不写汇编

画一个从低地址到高地址的表，例如：

```text
frame + 0*8   → x0
frame + 1*8   → x1 / ra
frame + 2*8   → x2 / 原始 sp
...
frame + 31*8  → x31
frame + 32*8  → sstatus
frame + 33*8  → sepc
frame + 34*8  → scause
frame + 35*8  → stval
```

具体 offset 以后汇编和 Rust 必须共用同一份事实，不能一边靠结构体顺序、一边靠人工记忆。

### A 次验收

- [ ] 能区分同步异常和中断。
- [ ] 能解释 `stvec/sepc/scause/stval` 各自回答什么问题。
- [ ] 能算出为什么当前 frame 是 288 字节。
- [ ] 能解释为什么 `x2` 需要记录“分配 frame 之前”的 sp。
- [ ] 还没有主动触发任何异常，普通启动保持正常。

## B 次：只把 trap 入口接好，不制造错误

### 第一步：创建两个文件，分清职责

计划创建：

```text
src/trap.S   → CPU 刚进入 trap 时必须做的汇编工作
src/trap.rs  → TrapFrame 定义、stvec 初始化、Rust 诊断逻辑
```

在 Rust 侧通过：

```rust
global_asm!(include_str!("trap.S"));
```

把汇编加入最终内核。

### 第二步：先把中断状态固定住

本阶段不依赖任何普通中断。初始化 trap 路径前显式保持相应 S 模式中断关闭，避免“固件留下的状态”变成课程隐含前提。

同步非法指令异常并不需要开启中断才能发生。

### 第三步：入口先分配 288 字节 frame

如果进入时 `sp` 已按 ABI 16 字节对齐，那么：

```text
288 = 18 × 16
```

减去 288 后仍保持 16 字节对齐，便于随后调用 Rust 函数。

但这里最容易犯一个经典错误：

```text
为了计算原始 sp
先拿 t0 做临时寄存器
↓
却还没保存 trap 发生时原来的 t0
↓
原始现场已经被自己破坏
```

正确思路是先把将要借用的临时寄存器保存到 frame，再用它计算旧 sp。用伪汇编表示：

```text
sp -= 288
save original t0 into t0_slot(sp)
t0 = sp + 288
save t0 into x2/original_sp_slot(sp)
再继续保存其他寄存器
```

不是要求照抄这几行，而是要求你能解释**为什么顺序不能反过来**。

### 第四步：保存整数寄存器，再读取 CSR

目标是不在保存前随便覆盖任何还没记录的寄存器。

整数寄存器槽位完成后，再用已经安全保存过的临时寄存器读取：

```text
sstatus
sepc
scause
stval
```

`x0` 不需要真的从硬件“保存”，槽位写 0 即可。

### 第五步：自动检查 Rust/汇编布局一致

在 Rust 中定义 `#[repr(C)] TrapFrame`。

至少增加：

```text
size_of::<TrapFrame>() == 288
```

的编译期或启动期检查；关键字段 offset 也应通过共享常量、生成常量或显式断言校验。

目标是：以后有人给 `TrapFrame` 加字段却忘记更新汇编时，尽早失败，而不是等第二次 trap 随机损坏。

### 第六步：调用 Rust 报告函数

frame 完整后，才把它的地址放入 ABI 的第一个参数位置 `a0`，调用固定符号名、`extern "C"` 的 Rust 函数。

只有在 frame 地址正确、对齐正确、所有字段已经初始化以后，Rust 侧才有资格把这块内存按 `TrapFrame` 解释。

当前报告函数返回 `!`，所以本课不写寄存器恢复和 `sret`。汇编在 Rust 调用之后仍保留一个不会继续乱跑的等待兜底路径。

### 第七步：安装 `stvec`

初始化函数把对齐的汇编入口地址写入 `stvec` 的 Direct 模式，然后输出：

```text
trap ready
```

此时**不要制造异常**。

运行：

```sh
cargo run
```

预期至少保留：

```text
Hello kernel
trap ready
```

如果安装一个 trap 入口本身就让正常启动坏掉，先修入口和初始化，不进入 C 次。

### B 次验收

- [ ] `TrapFrame` 大小和关键 offset 有自动检查。
- [ ] 能逐步解释保存原始 `t0` 与原始 `sp` 的顺序。
- [ ] 调 Rust 前栈满足约定对齐。
- [ ] `stvec` 指向真正的汇编入口，不是普通 Rust 函数。
- [ ] 未触发异常时正常启动，出现 `trap ready`。

## C 次：制造一次“能解释的”非法指令

### 为什么不用 Rust 空指针做实验

用 Rust 制造未定义行为，会把“CPU trap 实验”和“Rust 语言层 UB”混在一起。

所以本课用一段独立汇编，明确放置非法指令编码，并给触发位置一个标签。

### 第一步：添加受控触发点

例如在独立汇编函数中放置：

```text
trigger_label:
    .4byte 0
```

当前目标包含压缩指令扩展；全零编码在这里用于构造明确的非法指令实验。真正运行前仍以实际 `scause` 结果为准，而不是因为教材写了“应该是 2”就跳过验证。

在调用前打印：

```text
trigger at 0x...
```

### 第二步：Rust 诊断只打印事实

报告：

```text
[trap]
scause=...
sepc=...
stval=...
```

对于本实验，预期：

- `scause` 的 interrupt 标记没有设置；
- exception code 为 2（illegal instruction）；
- `sepc` 与 `trigger_label` 对应；
- `stval` 记录实际值，它可能是 0，也可能提供与非法指令相关的信息，课程不要求非零。

### 第三步：不要“顺手修复”然后返回

看到非法指令以后，不要写：

```text
sepc += 4
sret
```

来让实验“继续跑”。原因有两个：

1. 本课还没有设计完整恢复路径；
2. RISC-V 指令长度并不永远是 4 字节，当前目标支持压缩指令。

第 08 课只会对**已知固定长度的用户 `ecall`**做明确的返回地址前移规则。

### 第四步：考虑固件委派

CPU 当前从 OpenSBI 所在的 M 模式环境进入 neonos 的 S 模式。某类异常能否直接交给 S 模式处理，还受 M 模式异常委派配置影响。

如果触发后没有进入 neonos 报告：

- 先看 OpenSBI/固件输出；
- 核对 `stvec`；
- 核对当前 trap 是否被委派给 S 模式；
- 不要先假设一定是 UART 坏了。

### 第五步：恢复正常路径

实验成功后移除主动触发调用，但保留 trap 初始化和诊断能力。

再运行普通启动和：

```sh
./tests/boot.sh
```

## 常见问题

| 现象 | 先检查 |
| --- | --- |
| `trap ready` 都没有 | 普通启动是否已在安装入口前坏掉 |
| 触发后完全静默 | `stvec`、入口对齐、链接、异常委派 |
| `[trap]` 无限重复 | trap 处理器自己是否再次异常，frame/栈是否被写坏 |
| `sepc` 与 trigger 不一致 | 触发标签、CSR 保存时机、是否有更早异常 |
| Rust 字段像随机值 | 汇编 offset 与 `#[repr(C)]` 布局是否一致 |
| 进入 Rust 后马上异常 | ABI 栈对齐、参数地址、关键寄存器是否满足调用条件 |
