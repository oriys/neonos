# 第 11 课：谁先运行，怎么算“更好”

状态：待开始。前置：[第二阶段](stage-02.md) 验收完成。预计 45～60 分钟。

## 为什么先做模拟，不马上改内核

第二阶段一次只运行一个用户程序。现在如果有 A、B、C 三个 Ready 任务，内核第一次必须回答：

> **到底先运行谁？“更好”的调度又用什么数字衡量？**

如果一上来就写调度器，很容易把“选择策略”和“上下文切换代码”混在一起。

所以本课完全在纸上和宿主机模拟器中学习策略；第 12 课才改内核。

阅读 [OSTEP 第 7 章 CPU Scheduling](https://pages.cs.wisc.edu/~remzi/OSTEP/)，只关注 FCFS、SJF、RR 和响应/周转两个指标。

## 先定义四个时间点

对一个任务记录：

```text
arrival      到达/变成可运行的时刻
first_run    第一次真正拿到 CPU 的时刻
service      总共需要多少 CPU 时间
completion   完成时刻
```

然后：

```text
response time   = first_run  - arrival
turnaround time = completion - arrival
```

本课的 response 是“第一次拿到 CPU 有多快”，不是“第一次打印字符有多快”。

对于本课这种没有 I/O 的纯 CPU 任务，还可以观察：

```text
waiting time = turnaround - service
```

但阶段验收只要求 response 和 turnaround，避免一次引入太多指标。

## 手算：同一输入比较三种策略

三个任务都在 `t=0` 到达：

| 任务 | CPU service |
| --- | ---: |
| A | 6 |
| B | 2 |
| C | 1 |

SJF 使用**非抢占**版本；RR quantum=2；先忽略上下文切换成本。

### FCFS

```text
0      6    8  9
|------|----|-|
   A      B  C
```

响应：

```text
A=0
B=6
C=8
平均 = 14/3
```

周转：

```text
A=6
B=8
C=9
平均 = 23/3
```

### SJF

```text
0  1    3          9
|--|----|----------|
 C   B        A
```

平均响应：

```text
(0 + 1 + 3) / 3 = 4/3
```

平均周转：

```text
(1 + 3 + 9) / 3 = 13/3
```

注意：这个漂亮结果依赖一个很强的先验——调度器事先知道每个任务还要运行多久。真实通用内核通常不知道未来 service time，所以不能把这里的 SJF 结果写成“实际可实现的永久最优保证”。

### RR，quantum=2

```text
A 0-2
B 2-4 (完成)
C 4-5 (完成)
A 5-7
A 7-9 (完成)
```

平均响应：

```text
(0 + 2 + 4) / 3 = 2
```

平均周转：

```text
(9 + 4 + 5) / 3 = 6
```

这里没有“一个策略所有指标都总是最好”的结论。策略要结合工作负载和目标讨论。

## 宿主机模拟器

计划创建：

```text
experiments/scheduling.py
```

它运行在宿主机，不使用仓库默认的 RISC-V 裸机 target。

每个任务至少保存：

```text
id
arrival
service
remaining
first_run (初始为空)
completion (初始为空)
```

### 把模拟拆成四件事

不要把所有逻辑塞进一个巨大循环：

```text
1. 推进模拟时钟
2. 处理到达
3. 选择/重新入队
4. 结算统计
```

### 固定同一时刻事件顺序

模拟结果必须确定，不要让“列表遍历顺序”偷偷决定策略。

课程统一约定，在某个时间边界：

```text
1. 结算刚结束的运行区间/完成任务
2. 加入这个时刻新到达的任务（同刻按输入顺序）
3. 把 quantum 用完但未完成的旧任务放回队尾
4. 选择下一个任务
```

其他事件顺序也可以设计，但必须写清并在手算/代码中保持一致。

### 边界输入

必须覆盖：

- 空任务列表；
- 单任务；
- 两个任务同刻到达；
- 中间 CPU 空闲，下一任务晚到；
- service=0：约定 arrival 时直接完成，response=turnaround=0；
- arrival<0 / service<0：拒绝；
- RR quantum<=0：拒绝。

空队列但未来仍有任务时：

```text
clock 直接跳到下一 arrival
```

不要一格一格空转。

## 两个守恒检查

每次模拟结束自动验证：

```text
sum(实际 CPU 执行时长) == sum(service)
```

以及：

```text
对每个非零任务：
arrival <= first_run <= completion
```

有 CPU 空闲时，最终 completion 可能大于总 service，这是正常的。

## 常见问题

| 现象 | 先检查 |
| --- | --- |
| RR 每次重新运行都改 response | `first_run` 是否只在第一次赋值 |
| turnaround 只等于 service | 是否忘了等待时间也包含在 completion-arrival 中 |
| 同一输入每次顺序不同 | 同刻事件和平局规则是否固定 |
| CPU 空闲时模拟死循环 | 是否跳到下一 arrival |
| SJF 被描述成“真实内核绝对最佳” | 是否忘了它需要预知任务长度 |
