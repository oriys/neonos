# 第 33 课：等待一个条件，而不只是等待一把锁

状态：待开始。前置：[第 32 课](32-mutex.md)。分 A、B 两次，每次 45～60 分钟。

## 目标与阅读

阅读 OSTEP 第 30 章。参考 [Rust Condvar 文档](https://doc.rust-lang.org/std/sync/struct.Condvar.html) 理解“释放锁并等待、返回前重新持锁”，以及为什么调用方用 while 反复检查条件。内核实现使用自己的对象表和状态机。

## A 次：完成等待状态机

1. cond_create 绑定同进程一个有效互斥锁，并记录绑定引用。wait 与 signal 都要求调用者持有该锁。
2. 在一个不可抢占区间内完成登记条件等待者、释放互斥锁（可能交接其他锁等待者）和标记 Blocked。
3. 在线程中保存阶段 `WaitingCondition → ReacquiringMutex → Completed`，不是每次重试都重新释放锁并进入条件队列。
4. signal 从条件队列取一个，转到绑定锁的获取流程；只有真正取得锁后才完成 wait 返回。无等待者的 signal 不存储“以后可用的通知”。
5. 返回用户时清除待完成状态，前移原 ecall 一次。未返回之前需要调度多次，也不能重复通知或释放。

## B 次：有界队列

1. 在共享用户页放容量 4 的队列，所有队列字段由同一互斥锁保护，配两个条件变量 not_empty、not_full。
2. 生产者在 while 队列满时 wait；入队后 signal not_empty。消费者在 while 队列空时 wait；出队后 signal not_full。
3. 先一生产者一消费者，再两生产者一消费者；输入总量固定，消费者知道总项数，避免生产结束后无限等候。
4. 对每项赋唯一编号，验证无丢失、无重复、单生产者内部顺序正确，队列长度始终在 0～4。
5. 插入通知与实际条件不匹配的受控唤醒，检查 while 能回到等待；通知本身不承诺条件已经成立。
6. 测试容量 1、消费者先运行、生产者先运行和重复批次；销毁条件变量时拒绝仍在等待或重新加锁中的线程引用。

## 常见问题与验收

| 现象 | 先检查 |
| --- | --- |
| 消费者醒来却读空队列 | 是否用了 if 而没有重新检查条件 |
| wait 永远不返回 | 唤醒后是否遗漏重新加锁阶段 |
| 生产者等锁但锁没人持有 | 释放、交接与条件登记顺序是否一致 |

- [ ] wait 的释放与登记原子化，返回时持锁。
- [ ] 队列守恒条件和各种先后顺序通过。
- [ ] 无早期通知积累、无重复登记，更新 [进度记录](progress.md)。
