# 第 35 课：线程都活着，为什么谁也不前进

状态：待开始。前置：[第 34 课](34-semaphore.md)。分 A、B 两次，每次 45～60 分钟。

## 目标与阅读

阅读 OSTEP 第 32～33 章。能用等待关系解释死锁，通过一致锁顺序修复，并把一个等待流程改写成事件驱动状态机进行比较。

## A 次：可控复现和修复

1. 宿主机先用确定性模型安排 A 持 L1 等 L2、B 持 L2 等 L1，画出循环等待。避免依靠随机 sleep。
2. 内核负例使用测试调度门闩确保两线程各取得第一把锁；随后释放门闩，让它们申请另一把。门闩是测试工具，不写进锁实现。
3. 设置有限看门观察：输出线程状态、等待对象、各锁所有者。超时只表示没有按期完成，等待环才是本例死锁证据。
4. 在独立 QEMU 测试会话复现后结束会话，不让正常启动永久挂住。
5. 修复为统一按 L1→L2 获取。同步调整测试门闩，不能仍要求两线程都取得不同第一把锁后才放行，否则会由测试自身制造停滞。
6. 验证两线程均完成且计数正确；对比无环等待、死锁、饥饿与活锁的含义。

每次约 15 分钟推理、25 分钟实验、15 分钟复盘。统一顺序适用于约定覆盖的锁集合，不能据此声称消除了所有形式的死锁。

## B 次：事件驱动对比与总验收

1. 在计划中的 `experiments/deadlock.py` 或独立模拟中，把“等数据→处理→等输出空间”写成显式状态机。
2. 事件循环每次处理有界工作后返回；用相同输入比较线程等待版和状态机版的输出，说明长回调阻塞整个循环的风险。
3. 事件驱动实验不替换内核调度器，不自动获得多核并行，也不意味着完全不需要同步。
4. 新增 `tests/concurrency.sh`：将预期竞争结果、预期死锁负例和修复后完成场景分别判断；失败案例不能仅以超时作为通过。
5. 正例检查共享计数、队列完整性、许可上限、join、对象回收以及多轮重复后的资源基线。
6. 回归旧 shell 和管道，特别检查等待原因已由 PID 改为 TID 后没有误唤醒或重复回收。

## 常见问题与验收

| 现象 | 先检查 |
| --- | --- |
| 修复锁顺序后还是卡 | 测试门闩是否依赖旧的错误获取顺序 |
| 超时但等待图没有环 | 是否是外部事件缺失、逻辑错误或饥饿 |
| 事件循环输出忽快忽慢 | 单个回调是否长时间占用执行线程 |
