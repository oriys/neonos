# 第一阶段：让内核启动、说话和报告错误

状态：课程已安排，学习待开始。入口：[总路线](README.md) · [进度记录](progress.md)。

本阶段从仓库现有的 `Hello kernel` 出发。完成后，你能解释启动流程，用自己的打印工具输出信息，并在 panic 或受控 CPU 异常时找到错误线索。

## 各课如何衔接

第 01 课的启动输出用于保底检查；第 02 课的打印工具供后续各课复用；第 03 课给软件主动报错；第 04 课保证启动数据初始化并解释栈；第 05 课处理 CPU 报告的异常。

第 02 课才创建 `src/console.rs`，第 04 课才创建 `src/memory.rs`，第 05 课才创建 `src/trap.rs` 与 `src/trap.S`。这些是课程中的计划产物，本次安排只准备教材。各课代码片段是局部示例，按步骤逐项接入并验证。

## 通用操作

在项目根目录运行 `cargo build` 检查编译，`cargo run` 观察行为。退出 QEMU：先按 `Ctrl-A`，松开，再按 `X`。恢复普通启动路径后运行 `./tests/boot.sh`。

现有启动脚本看到 `Hello kernel` 就会通过；它不能证明之后没有 panic，也不能验证 BSS 清零或异常报告。每课必须另外检查本课目标输出。主动制造错误的实验完成后，移除触发代码再验收正常启动。

## 第一阶段总验收

- [ ] 能从 QEMU 一直讲到 `rust_main` 和 UART。
- [ ] 打印字符串、整数和地址，无需依赖标准库。
- [ ] 主动 panic 时能看到消息和源代码位置。
- [ ] 能区分代码、只读数据、可写数据、普通 BSS 和启动栈。
- [ ] 用实际实验验证 BSS 清零范围，不只看初值本来就是零。
- [ ] CPU 异常报告包含原因、指令地址和辅助信息。
- [ ] 去掉实验触发代码后正常启动，原启动检查通过。
- [ ] 在进度记录中留下实际输出、解释和未解决问题。

进入第二阶段前自问：软件主动调用 `panic!` 和 CPU 发生异常有什么区别？它们为什么都需要已经可用的输出工具？
