## 各课为什么按这个顺序

不是因为“教材目录刚好这样排”，而是每一课解决上一课暴露的问题：

```text
已有 Hello kernel，但不知道为什么能启动
  ↓ 01
能解释启动，但输出代码写死在 rust_main
  ↓ 02
有通用输出，但 Rust 失败仍静默
  ↓ 03
panic 会说话，但 CPU 异常还没有入口；先搞清栈和内存
  ↓ 04
知道可信栈和布局
  ↓ 05
可以接住、保存并解释一次 CPU 异常
```

第 02 课创建 `src/console.rs`，第 04 课创建 `src/memory.rs`，第 05 课创建 `src/trap.rs` 与 `src/trap.S`。这些是学习过程中逐步产生的代码，不因为教材文件已存在就视为功能已实现。

## 本阶段的共同实验规则

1. **一次只改一个层次。** 例如先让 `put_byte` 工作，再做 `write_str`，不要同时写完宏和 panic。
2. **先预测，再运行。** 预测错了不是失败，无法解释实际结果才需要继续调查。
3. **正例和负例都要做。** BSS 需要“清零/不清零”对照；trap 需要“正常启动/故意异常”对照。
4. **实验触发代码最终移除。** 故意 panic、非法指令、probe 填充完成后恢复正常路径。
5. **测试结果按实际覆盖解释。** 当前 `./tests/boot.sh` 看到 `Hello kernel` 就成功，它不能证明后续没有 panic，也不能验证 BSS 或 trap。
6. **记录第一条异常现象。** 不要看到“没输出”就同时改入口、链接、栈和 UART。

## 通用操作

在项目根目录：

```sh
cargo build
cargo run
./tests/boot.sh
```

退出交互 QEMU：按 `Ctrl-A`，松开，再按 `X`。

修改 `linker.ld` 后如果怀疑复用了旧链接产物，可以显式：

```sh
cargo clean
cargo build
```

## 第一阶段总验收

### 能运行

- [ ] `cargo run` 从 OpenSBI 进入 neonos 并输出正常标记。
- [ ] `print!` / `println!` 能输出字符串、整数、十六进制地址和空行。
- [ ] 故意 panic 时能看到消息与真实位置，恢复后正常启动。
- [ ] 内存边界输出合理，普通 BSS 与启动栈不重叠。
- [ ] BSS probe 能得到“填非零→清零后为零”的真实对照。
- [ ] trap 入口安装后普通启动仍正常。
- [ ] 受控非法指令得到一次可解释报告，`sepc` 对应触发点。
- [ ] 删除所有临时触发后，原启动检查通过。

### 能解释

进入第二阶段前，不看教材回答：

1. `cargo run → QEMU → OpenSBI → _start → rust_main → UART` 每一步是谁负责？
2. 为什么格式化和发送 UART 字节是两个层次？
3. Rust panic 和 CPU trap 为什么不是同一个入口？
4. 为什么 BSS 是零不能自动证明自己的清零代码运行过？
5. 为什么 trap entry 不能直接当普通 Rust 函数调用？
6. `stvec/sepc/scause/stval` 分别告诉我们什么？
7. 当前 `boot.sh` 通过到底证明了哪些事情，没有证明哪些事情？
